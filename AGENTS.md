# Cuisine: notes for agents

Read README.md first. Personal or machine-specific workflow rules, if any, go in an untracked `CLAUDE.local.md`, never here.

## Architecture rules

- `src/domain` is pure TypeScript: no I/O, no Node or browser APIs. Business rules go here, with tests next to each module (`use-by.ts`, `use-by.test.ts`) and shared fixtures in `test-fixtures.ts`.
- Use cases in `src/server/application` depend only on the ports in `application/ports/`, one file per area, reached through `Deps`. Adapters live in `src/server/infrastructure` and are wired up only in `src/server/container.ts`; the first-run seed is a startup step in `main.ts`.
- The client imports from `src/domain` and `src/shared`, never from `src/server`. `src/shared` is types only; the server builds them (`application/recipe-views.ts`). Ports don't use its API shapes.
- One concern per file; keep files short. Routes go one file per area under `src/server/http/routes`: they parse, call one use case and shape the response. Request schemas shared between routes, or too long to read inline, go in `http/schemas`.
- The server runs TypeScript directly with Node 24 type stripping: erasable syntax only, explicit `.ts` import extensions, and no build step for the server.

## Facts worth knowing

- Recipes are markdown files (`recipes/` in the data directory). Only `## Ingredients` is parsed. The line grammar is in `src/domain/ingredient.ts`, and the item name is what matches the pantry.
- Automatic planning follows the trips: on the morning of a grocery run it plans that trip's window (`domain/trip-plan-run.ts`), and a nightly top-up fills today and tomorrow. Each has a switch in Settings → Planning (`domain/automatic-planning.ts`, `application/automatic-planning.ts`). `application/plan-catch-up.ts` applies the same choices on a restart, and `shop-day.ts` to a changed trip.
- The Plan tab (route `/week` and tab id `week`, kept because installed phones and notification links use them; `screens/WeekScreen.tsx`) shows one trip window, from a trip through the day before the next (`tripWindow`, `previousTripWindow`, `nextTripWindow`), so a moved trip makes it shorter or longer. "Plan the rest of this trip" is `POST /plan/fill-trip` (`planTrip`): from today through the end of the window on show, so it can go past `planHorizonEnd` when someone asks for a later trip, up to `FARTHEST_TRIP_DAYS` ahead.
- Clearing the plan (`domain/plan-clear.ts`, `application/clear-plan.ts`, `screens/week/ClearPlan.tsx`, `GET` and `DELETE /api/plan/upcoming`) takes off meals and extras from today on, pinned ones too, in one transaction. It never touches past days, anything with an outcome, or an entry that came off the pantry and was unticked, since taking that off wouldn't put back what it used. Leftovers of a meal coming off go with it, or lose their source if they stay. The list and reminders read the plan afresh. It holds automatic planning (`held`) until someone taps a plan button, saves an import or chooses Start again in Settings, so a cleared plan stays cleared through the top-up, trip mornings and restarts. A run already going when it's cleared can still fill what came off.
- Claude calls are single structured-output requests (`src/server/infrastructure/ai/claude.ts`) through `ask.ts`: `claude-sonnet-5-5` with the server-side refusal fallback, and `config.fastModel` (`CUISINE_FAST_MODEL`, `claude-haiku-5-5`) for recipe imports (link, photos, words; not Claude's own picks), `nightBeforeSteps` and the page fetcher, which Haiku can use with `web_fetch_20250910`. Haiku has no server-side fallback, so it is sent without the beta, and a `refusal` from it is retried once on the main model with the fallback. With no key, the rotation planner takes over.
- All dictation goes through one place: `DictationProvider` on the client (a bar that persists across screens), `useDictationSession` (record → keep → transcribe → interpret), `POST /api/listen` with the words and a `ListenContext`, and `application/listen.ts`. Add a new mic button by calling `useDictation().start(context, label)` (or `useFieldDictation(field, label, into, ready)` for a text field); don't build another recorder screen.
- Days before the next shopping trip (`beforeGroceries`) only get recipes that are ready at their batch size. Stock `low` means enough for this batch but running low, and doesn't stop that; `short` means known amounts fall short for this batch, and grades like missing. A planning run holds those days to one pantry (`application/pantry-for-planning.ts`, `domain/running-pantry.ts`): counts and measured portions come down for meals already planned and each meal it chooses; plain have/low items don't. The recipe screen's status and `keepPlanCookable` still judge one meal at a time, so meals already planned are never taken off for adding up. `pinned` entries were chosen by a person and are never replaced by `keepPlanCookable`, which takes unpinned leftovers off with their dinner. Pinned leftovers stay with `leftoversOf` cleared and show as plain leftovers.
- Leftovers follow what actually happened (`domain/leftovers.ts`, `application/leftovers-follow.ts`). `madeName` says whether a meal was really made, recipe or only a name; only those are offered as leftovers (`madeTitle` on the view, the swap sheet), and `placeChoice` refuses others. When a meal is skipped or turns out to be a different dish (`recordMeal`, `finishCooking`, `placeMeal`, compared by `sameDish`), planned leftovers still to come are removed and pinned ones lose their source. The slot is open for the normal rules. Nothing restores them when the meal is marked made again, and a meal going back to its plan goes back to its own size (`sizeWithoutSwap`). Eaten leftovers are never touched. "Any dinner left?" at the top of the check-in's pantry step (`domain/dinner-left.ts`, `application/dinner-left.ts`, `screens/checkin/AnyLeft.tsx`, `PUT /api/checkin/:date/any-left`, kept in `household_settings.dinners_left`) decides what's offered (`leftoversOffered` on the view): a dinner from the book is offered unless someone said none, and one that's only a name only after a yes, since it might be "Eating out". None also takes planned leftovers of it off, as above. A yes goes to the dice as `leftovers`; nothing assumed does.
- Moving a meal (`domain/meal-move.ts`, `application/move-meal.ts`, `POST /plan/:date/:slot/move`, `ui/MoveMeal.tsx`) takes the same slot on another day and trades places in one transaction. The whole entry moves and both are pinned. Meals with an outcome, or that came off the pantry (`stillOnlyPlanned`), can't move or be traded with, a past day isn't offered, and a meal on a past day can only go to an open one. Leftovers of either meal follow it when they still come after it within `LEFTOVERS_LAST_DAYS` (`leftoversFit`); otherwise planned ones come off and chosen or eaten ones lose their source. A dish's leftovers trading into a day before it come off unless chosen. `moveOptions` runs the same rules for the row's words, on the days from `moveDays` (the rest of the trip, and always three ahead).
- What came off (`domain/came-off.ts`): `setMeal` answers with `cameOff` when a recipe nobody made was replaced by another dish, and `CameOffOffer` shows a line under the meal that nobody has to answer. The client holds the meal for that moment, and `POST /plan/came-off` (`putBackMeal`) places it. There's no trade here, since its old slot has what replaced it: it takes the place of what's on the chosen day, and that meal gets the same offer in turn.
- A trip nobody recorded (`domain/trip-in-house.ts`, `application/pantry-with-trip.ts`): until someone puts things away for it (list or stock-up) or applies a receipt to it, the latest trip that has happened has its saved list counted as in the house, by `cookableCheck`, `pantryForPlanning` and `plannerContext`. It's never saved to the pantry, and the recipe screen doesn't see it. A trip's own day has none: that trip hasn't happened, and the one before it ended. A moved trip is out of the schedule, so it counts from its new day. A counted line adds its saved `quantity`, or `COUNT_ASSUMED_BOUGHT` on lists from before that was kept. A put-away the day after a trip lands on the next trip's list (`markBought`), so it doesn't record the one before.
- Meals taken off by themselves (`domain/meal-off.ts`, `application/meals-off.ts`, `household_settings.meals_off`): `keepPlanCookable` remembers what it replaced, and the `meals-off` job says so once a morning through `notifyOnce`, keyed by the date, from the plan time (never before 6 AM) for four hours. Anything coming off after that morning's notice waits for the next. `MealsOffNote` on the Day screen says the same in one line ("Lunch changed to X — no tortillas for Y", the replacement from `mealsOffView`), with "Put back on the plan" (`putMealBack`), which pins the meal at its size, and a × that dismisses it (`dismissMealOff`, `POST /api/plan/:date/:slot/dismiss-meal-off`). Its leftovers stay gone, as they do when a meal is marked made again. A note stops standing once it's dismissed or put back, its day has gone, the slot is pinned or has an outcome, or the plan is cleared, so a person's own change never gets one.
- Cooking mode (`RecipeScreen`, `useCookSession`) is view-only: it keeps the screen awake and lets you cross things off, and its Done button just leaves it. It records nothing; meals are marked made through the check-in. The `cooked` `ListenContext`, `settleCookedMeal` and `plan_entries.pantry_settled` (a saved cook review settled the meal) are left from when it did, with no screen that sends them. `plan_entries.pantry_settled` is checked by the check-in so it doesn't ask again. `plan_entries.checkin_settled` marks meals a check-in has been through. A check-in also goes through earlier meals that were cooked and left unsettled, up to `CARRY_OVER_DAYS` back (`mealsToSettle`), so a meal cooked after its day's check-in, or on a day with none, comes off at the next one and only once. A cook review of a dish the check-in already settled changes nothing (`settledByCheckin`): `listen` answers without the model, and `applyProposal` leaves the pantry alone. Migration 17 marked everything recorded before it, so old meals never come off.
- Check-in rows (`screens/checkin/MealRow.tsx`, `domain/checkin-marks.ts`, `application/checkin-meal.ts`, `PUT /api/checkin/:date/:slot`) mark one meal Made, Skipped or Something else, with no model. A typed name goes in `note` with `outcome: swapped` and no `outcomeSlug`, so nothing comes off for it, and leftovers follow (`leftoversFollow`); a meal planned only as a name keeps that name in `household_settings.checkin_planned_notes` meanwhile. Settled meals are read-only, here and on the server. Extras get Made and Didn't make it, which takes them off. Once every row is marked the main button reads Continue, the same `confirmPlannedMeals`.
- Catching up (`domain/checkin-catch-up.ts`, `application/checkin-catch-up.ts`, `earlier` on `CheckinView`, `screens/checkin/CatchUpQuestion.tsx`): before a day's meals step, the check-in asks about each earlier day in `CARRY_OVER_DAYS`, on or after the first check-in on record, with meals nobody marked, latest first. Yes is `confirmPlannedMeals`, so the pantry step's `carried` covers it. No is kept in `household_settings.checkin_catch_up_no` and opens that day's rows (`CatchUpDay`); it means anything not marked stays unrecorded and comes off nothing, and that day isn't asked about again, though its own check-in stays open. A day's pantry step closes once a later check-in has settled it (`finishEarlierDays`).
- Importing a written meal plan (`domain/plan-import*.ts`, `application/plan-import*.ts`, `screens/PlanImportScreen.tsx` and `screens/week/`, from the Plan tab): the form starts with the days being planned (`defaultImportRange`: the next trip through the day before the one after), then a photo, words or field dictation goes to `readMealPlan` in the background like a receipt, one import at a time, kept as JSON in `household_settings.plan_import` (`plan-import-record.ts`, which also brings a record saved with `weekStart` and `weekday`s up to date); photos aren't kept, so only words can be retried. The plan's text is data: `checkedMeals` lets through only recipes in the book and real dates, turns any other slug into a name marked unsure, and never writes a recipe. Days are worked out in code, not by the model: `datesInWrittenOrder` walks the lines from the range's start, so a named day is its first occurrence on or after the last day reached, a written date wins and moves the walk, and a line with no day stays without one. Meals past the end of the range keep their dates. The review saves nothing and shows one day to a screen (`PlanImportPager`, CSS scroll snap, `reviewDays`, with a strip over the back gesture's `EDGE` so that keeps working); `plan-import-choices.ts` holds what has to be decided. Two meals in a slot get Use this (`chooseMeal`), a meal with no day has to get one or go, and either stops Save with a line saying so; replacing something planned is the default, with Keep to drop the imported meal instead. Confirming (`confirmPlanImport`) is one transaction, through `placeChoice` and `addExtra`, so everything is pinned; it skips days gone by and meals already recorded, refuses two meals in a slot, and works once per import, so extras can't double. Leftovers from a plan are plain (`leftoversOf: null`) and don't double the dinner before them. "Fill in the rest" is `POST /plan-import/fill`, a separate choice on the saved screen. `claudesIdeas` on the record, off from the form's switch, holds that import to the book, kept picks included: unkept picks aren't offered to the model or the review's picker, a match on one becomes a name, confirming refuses one, and filling in runs with `bookOnly`, where `fillPlan` drops `new` and `note` answers and writes nothing. A book-only request never joins a run that can invent dishes (`runCovers`), and a merged one stays book-only. All other planning is as it was. "Tell Claude what to change" on the review (`usePlanRevision`, `application/plan-import-revise.ts`) sends what they said, the day on screen and the rows as they stand; the answer replaces the rows with an Undo, and nothing saves until Save.
- A recipe's `meals` (`RecipeMeal`) are breakfast, lunch, dinner and `extra`. Extra means it isn't a meal on its own, so no planner uses it: go through `plannableMeals` when planning, and a recipe with no plannable meal stays out of `plannerContext` and `validPlan`. The rule Claude tags by is `RECIPE_MEALS_RULE` in `ai/prompts.ts`.
- Extras (`domain/plan-slot.ts`, `application/plan-extras.ts`): anything else someone means to make on a day, in any number. Each is an ordinary `PlanEntry` with the slot `extra-<id>`, stored in its own table, `plan_extras` (`infrastructure/db/plan-extras-table.ts`, migration 19); `plan_entries` keeps its one meal per date and slot, and only the plan repository knows about the two tables. `range` returns meals then extras, so a path that walks the plan gets extras unless it uses `mealsOnly`. Only a person adds one: `fillIfOpen` refuses them, and anything choosing what goes in a meal's slot (`setMeal`, rolls, swaps) takes `MealSlot`, not `PlanSlot`. They're always pinned, have no leftovers and no draft. They feed the list and the budget, count in `pantryForPlanning`, and come off through cook mode, Done and the check-in like any meal, once. Until someone says one was made the check-in asks nothing about it (a planned meal is assumed eaten; an extra may still be coming). Save money never offers a swap of one, and the planner sees them only as `slot: 'extra'` in `alreadyPlanned`. An extra's slot is never reused, and one that's come off the pantry can't be changed or taken off.
- A recipe file that can't be read is left as it is, logged, and named on the Recipes screen (`RecipeRepository.problems`, `GET /api/recipe-problems`, `domain/recipe-file-problem.ts`). Only the file's name and fixed wording for its `kind` go out, never a parser's or the file system's message, since those quote the file or a full path. There's no way to delete from there.
- Icons come from `lucide-react`. Back navigation is an edge swipe; there are no back buttons.
- Navigation lives in `src/client/navigation`. Every in-app link that isn't the tab bar uses `TabLink` or `useOpen`, which record the tab and the screen to go back to; `useBack` returns there (stepping through history when it lines up, replacing otherwise). Don't use a bare `<Link>`/`navigate` for in-app screens, or back will leave the tab.
- `GET /api/shopping` only reads. Each load of the Shop screen (`screens/shop/load-list.ts`) also sends `POST /api/shopping/opened` (`application/list-opened.ts`), which saves the list and stock plan for the trip and starts reading unread Walmart package sizes. The server works out the list itself each time, so nothing the client holds can be saved. Aldi prices are the screen's own `POST /api/shopping/prices/refresh` when a read says `aldiLookup: 'due'`. A read that says `running` means someone else's lookup, so the screen polls with plain reads and reloads once when it ends (`screens/shop/lookup-poll.ts`).
- The list can be edited for a trip (`domain/trip-edits.ts`, `application/trip-edits.ts`, routes in `routes/shopping-lines.ts`, kept in `trip_plan:<date>` so it all moves with the trip and starts over with the next). Have it (`lineInHouse`) changes the pantry through `updatePantryItem`, by the list as it stands, so a repeat does nothing: a count rises to what's needed and at least to reading as have, portions go back to "some", no item makes an as-needed one. A line the pantry can't clear (a counted item a recipe doesn't count) goes in `skipped`. Not this trip (`skipLine`) keeps the key in `skipped`: `shoppingWeek` takes those lines out of `lines`, the total, the budget, the cart link, stock up and the saved trip list, and returns them as `skipped`. Add something (`addOneOff`) is a one-off keyed `o:<words>`, so adding twice is one line. It takes the week's store and goes under Other unless a pantry item has that exact name (`itemNamed`), when it uses that item's aisle, price and store. With no item it never gets one: its price and product live on the record (`changeOneOff`), price lookups skip it (`canLookUpPrice`) and buying it only leaves it on the trip's record. A receipt can still propose it as new, like anything else on a receipt. "$N over" offers Choose what to skip (`screens/shop/TrimSheet.tsx`, `trimChoices`): known prices only, restocks first, using the same skip.
- Ticks are saved per line against the trip (`application/trip-ticks.ts`, `PUT /shopping/ticks`, `checked` and `tickRev` on the trip plan), separately from Put away, which clears only the lines it did. A tick says what the line should be, never flips, and a late one for a trip that's over is dropped. On the phone `screens/shop/tick-sync.ts` keeps one queue that outlives the screen and a reload (localStorage): shown at once, sent one at a time, retried with a growing wait, and mentioned only after about 40 seconds (`TicksNote`). `tickRev` stops a read that left before a tap from unticking it. While the list is on screen `useListRefresh` looks every 20 s with a plain `GET /shopping`, through `useLoad`'s `refresh`: never through `loadShoppingList`, or every look would also send `/opened`. A tick on a line that has left the list isn't counted for Put away.
- `buildShoppingList` and `shoppingWeek` order lines along `STORE_WALK` (`domain/shop-sections.ts`), which must hold every name in `CATEGORIES`; an unknown category counts as Other. `ShopLines` and "Copy list" (`copyList`) both go through `shopSections`.
- `useLoad(key, load)` caches by key and refetches on any `announceChange()`, on waking after 20 s away, and after failures. GET requests time out after 15 s. Call `announceChange()` after any write made outside the screen that shows it.
- Shopping trips are dates (`shop_trips`, `domain/shop-schedule.ts`), never a weekday setting. After the last one on record the next is a week later, and so on; with none, `SHOP_WEEKDAY` starts the rhythm. Always go through `shopSchedule(deps)`. `application/shop-day.ts` `moveTrip` puts one trip on another day: earlier implied trips go on record, later ones drop, and the trip's store, saved list, trip plan (ticks, skips and one-offs too) and sent cart go with it. It's reached from the Plan tab's Next trip chip, Settings → Shopping and the evening prompt. On a trip day the morning notice names the next trip (`domain/trip-notices.ts`), and an hour before the check-in, with no receipt yet, the phone asks for the receipt and offers "we didn't go" (`screens/shop/TripCheckScreen.tsx`).
- Settings has this phone's text size, typeface and appearance on its main screen (`SettingsScreen`), then a row per group (`settings/SettingsMenu.tsx`, words from `setting-summaries.ts`) pushing a real route under `/settings/...`: `household`, `shopping` (and `shopping/move`), `cooking`, `stock-up` (`stock-up/add` picks from the pantry, `stock-up/:itemId` is one goal), `avoided`, `notifications`. They stay in the tab Settings was opened from, with no tab lit, and `parentOf` knows each parent for when the app opens straight onto one. New settings go in a group's screen, or a new row, not on the main screen.
- Forms: `.field` and `.button` take their height, padding and radius from `--control-*`, and spacing from `--space-*` (`styles/theme.css`, `styles/forms.css`). `ui/FormField.tsx` is a label, a control and a line of help. A save says what became of it through `useSaveState` and `SaveNote`/`SaveBar`. Back is a swipe, so forms saved with a button also use `useSaveOnLeave`: leaving keeps the changes. The ZIP doesn't, because saving it calls out and forgets looked-up prices, and neither does a new goal, where leaving means changing your mind.
- Substitutes are hard-coded in `domain/substitute-rules.ts`, per amount of the original. Chosen swaps (`ingredient index → option id`) live in the recipe's cook session and travel as `?subs=` and in the cooked `ListenContext`. Nothing records them on a meal now (finishing cooking is gone); earlier meals keep them (`plan_entries.substituted`), so the check-in takes off what was used (`ingredientsUsed`) even with no review; they're cleared when the meal turns out to be a different dish or isn't done after all.
- Aldi prices can come from aldi.us's undocumented Instacart GraphQL API (`infrastructure/prices/aldi.ts`), by the ZIP in Settings → Shopping, rechecked weekly (`needsLookup`); items Aldi doesn't carry are remembered for a week (`lookup-misses.ts`). Typed prices (`item_prices.source = 'typed'`) always win. Changing or clearing the ZIP forgets looked-up prices and misses, never typed or receipt ones. An item removed during a lookup stays removed. No AI price estimates.
- The Aldi lookup and the Walmart product read stay in the code, off by default, by the owner's decision. `ALDI_PRICE_LOOKUP` and `WALMART_PRODUCT_LOOKUP` turn them on; off, `deps.storePrices` and `deps.walmartProducts` are null, so no call is possible, and nothing is recorded (no misses, no empty `packSize`), so turning one on later just works. Both send a browser's user agent, and the README says so plainly. Keep the README's warnings accurate when this changes. Don't make either one default to on, and don't add a hosted or commercial use.
- `findPantryItem` picks what a recipe means: exact name, then a pantry name inside the ingredient ("all-purpose flour" → "flour"), then an item's `alsoCalled` names ("jam" → "raspberry preserves"), and only then a more particular kind. Ties go to what's in stock, and an also-called match in the house stands in for a best match that's out; the same goes for a regular item's restock line (`standingIn`, whole names only). Name variations belong in `alsoCalled` (editable per item, and set by Listen), not in code; different things you'd cook with differently belong in `substitute-rules.ts`.
- A recipe's `seasons` (frontmatter, `domain/seasons.ts`) default to all year, and the Sonnet import tags them. The planner keeps to them through `cookableCheck`; someone choosing a recipe themselves isn't stopped, only told. Toppings are per-ingredient `(optional)`, and required unless the source or family says otherwise.
- `occasional` pantry items (the "As needed" chip) are bought now and then: being out doesn't put them on the list, only a recipe needing them does. Having one doesn't change that: only the Keep stocked box (See all on the item) or saying so in dictation (`keepStocked`) makes it regular. New items dictated as on hand start this way too.
- `useBy` is one optional date per pantry item, the soonest (`domain/use-by.ts`). `lastsDays` sets an estimated date each time an item is restocked; going out clears the date. Writes must go through `updatePantryItem`, not `deps.pantry.update`, or these rules get skipped. A date only flags an item: nothing marks food out on its own.
- `portions` (`domain/portions.ts`, table `pantry_portions`) keep one item fresh, frozen, canned and dried, each with an amount and date (and `canOz`, ounces per can): recipes see the total (`shareNeeded` in `domain/portion-amounts.ts`), and the item's `useBy` is its soonest portion's. Cans compare by count, or by ounces when a size is known; dried converts at about 4 cans to the pound. An unknown amount ("some") or a measure that can't be compared falls back to the item's status. Things sold only frozen and shelf goods like flour stay plain items. The check-in and cook mode take down what meals used, fresh first, whole cans at a time; shopping sets the amount of the way it's bought back to "some" (`restocked`).
- Moving stock (`domain/portion-move.ts`) swaps fresh and frozen only, and never changes the total; what can't be added up is refused rather than guessed. Freezing leaves the fridge's date behind, so a past-date item stops reading as past once frozen. Thawing starts the clock from `lastsDays`, and a sooner date already on the fresh stays. A plain or counted item counts as fresh and becomes portions when moved. Adding (`domain/portion-add.ts`) raises the total. Both are `move` and `add` on `updatePantryItem`, worked out by the server from what's stored, unlike `portions`, which say how things should be. The panels call the same functions to say what will happen before it does.
- The expanded pantry row (`PantryItemEditor`) holds only what's changed standing in the kitchen; See all (`ItemDetailsSheet`, kept on the screen so changing the category doesn't close it) holds the rest. An open row stays where it is even if it no longer belongs in Use soon (`open-row.ts`). Typed fields use `useSavedField`, which shows Save until the server has the value and saves on blur, Return and closing. Every `input[type=checkbox]` is styled in `styles/checkbox.css`, with the tick drawn in CSS because the CSP refuses `data:` images.
- Trips (`domain/receipts.ts`, `application/receipts.ts`): `trip_lists` saves the list as it stood for each trip, because the live list recalculates; checked-off lines stay on it. A receipt is kept first (`receipts/` in the data dir), read by Sonnet in the background against the list, then the pantry, then proposed as new, and changes nothing until someone saves the review. Long screenshots are cut into overlapping pages for the model. Pharmacy and health items are left out on purpose. Saving a receipt makes each line's price per package the estimate for next time (`item_prices.source = 'receipt'`, for Aldi or Walmart), unless someone typed their own. Saving also marks its lines as in the house, so an older receipt defaults to Prices only (`savePricesOnly`), which leaves the pantry alone, isn't a trip, and doesn't keep the receipt. That's where Walmart prices come from: there's no lookup, and no AI price estimates. `trip-learning.ts` only suggests setting changes, after 3 trips. What checking a counted line off added (`TripLine.addedCount`) is credited against a receipt once, then goes to 0, however many receipts or lines follow (`creditCheckOff`). A check-off the saved list has no line for gets one (`checkedOffLine`). The app sends a token with each put-away, kept until it succeeds, and `put-away-requests.ts` remembers which lines each token did, so a retry adds nothing even after a receipt moved the count or the day turned over. `countAfter` is only the fallback for requests with no token.
- The receipt review (`screens/shop/ReceiptReview.tsx`) holds one `ReceiptRow` per line (`domain/receipt-review.ts`): name, kept, never add, and what it was bought instead of. Taps and Claude both go through `settleRows`, so only a line matched to nothing (list or pantry) can be never added, and a substitute must be a kept line standing in for a list line the trip's receipts don't have, one each. Save sends `choicesToSave` to `POST /receipts/:id/apply`; nothing is stored before it, never-adds included.
- Never add (`domain/never-add.ts`, `application/never-add.ts`, `receipt-never-add.ts`, `household_settings.never_add`, `GET`/`DELETE /api/never-add`, Settings → Shopping): left out in code after the read, at view time (`leftOut` on `ReceiptView`), never by the model. A line matches on its whole normalized printed words or its whole name (`productKey`), never part of one, and only when it's matched to nothing. Bringing one back is for that receipt only.
- Substitutes (`receipt-substitutes.ts`, `stand-ins.ts`): the bought line keeps its own name and goes in the pantry as itself; the list line's item is untouched. The saved line gets `insteadOf` (the list line's key), so `tripDiff` and trip learning count the list line as bought. The bought item gets the list line's name in `alsoCalled`, so `findPantryItem` and the list's restocks (`standingIn`) take it for the original while it's in the house. "Always fine instead" leaves the name for good; "Just this time" also notes it in `household_settings.stand_ins_for_now`, and `updatePantryItem` takes the name off once that item runs out. Prices only ignores substitutes.
- "Tell Claude what to change" on the receipt review (`useReceiptRevision`, `application/receipt-revise.ts`, `POST /receipts/:id/revise`) is the plan import's pattern: `useClaudeRevision` (shared with plan and recipe revisions), `ui/TellClaude.tsx` (the mic, plus a typed line here) and `ui/ClaudeNote.tsx` (Undo). The receipt and the words are data: `checkedRevision` holds the answer to the rows and pantry names. Words about a recipe come back as `recipe`, shown as one line linking to `/recipes/:slug?tell=…`, which opens the editor with the words on a one-tap button (`CarriedWords`); recipes are never changed from the receipt.
- Roll the dice (`application/pantry-meal.ts`, `domain/drafted-meal.ts`, `RollDice` on the swap sheet): Sonnet drafts a meal from what's in the house, either a ready recipe plus sides or things thrown together, and nothing saves until someone taps Use this. `plan_entries.drafted` keeps its how-to and `uses`, the amounts it expects to take. With a recipe, `uses` covers only what the recipe doesn't, so nothing comes off twice. `uses` apply only when the outcome is `made`, at the check-in's pantry step, already answered with what the model expected. Saying it went differently replaces `uses` through `MealUpdate.uses`.
- Claude's picks (`application/claudes-picks.ts`, `claudes_pick: true` in frontmatter): a dish Claude invents becomes a real recipe through `writePick`, whether it came from the planner (`kind: new`), a roll with no `recipeSlug`, or "write up" on a slot that's only a name. A roll built on an existing recipe stays with that meal in `drafted`. Picks stay out of the rotation until kept (`keepPick`). `avoided_meals` holds what they said not to suggest, with reasons, and goes to the planner and the dice. `recipeFromDescription` also backs "Describe it" on the import screen, whose recipes aren't picks.
- Kitchen notes (`application/kitchen-notes.ts`, Settings → How we cook) are the family's standing rules, in their words. `ask` adds them to every Claude call's system prompt as one labeled block, "Family rules (from Settings → How we cook)" (`ai/family-rules.ts`, `withFamilyRules`), so no call can leave them out: `write` for calls that plan or write (they guide the output and outrank any source text), `read` for calls that read what someone said (they help interpret names but aren't pantry news). Every new call picks one. Household rules belong in the notes rather than hard-coded in `prompts.ts`. Only the page fetcher gets nothing private; see `recipeFromPage` below.
- Who the household is (`domain/household.ts`, `application/household-profile.ts`, Settings → Who's eating) is one JSON value, `household_settings.household_profile`: `family` in plain words, `portions`, `dinnerTime`, `members`. It feeds the prompts and `portionsMultiplier`; go through `batchFor(deps, serves)`. No family's details belong in code or in prompts.
- A brand-new install gets `seed/` once (`infrastructure/seed.ts`): salt, water and starter recipes. The `first_run_done` marker stops it ever running again, and an install with anything in its pantry, recipes or plan only gets the marker.
- The data directory (`config-values.ts`) defaults by platform, and `~` is expanded in path settings because `.env` files don't. HEIC receipts need macOS's `sips`; elsewhere they fail with a plain message.
- Planning at startup runs after the server is up (`catchUp` in `main.ts`), because it can write recipes. Each planning run writes at most `NEW_DISHES_PER_PLAN`. All planning goes through `application/planning.ts`, one run at a time; a run only fills slots still open when the model answers (`fillIfOpen`), so anything done to a meal meanwhile stands.
- Scheduled jobs (`application/jobs.ts`) count as done only once the work succeeded: a failed run retries after 5 minutes and one lost to a restart after its 15-minute lease, within the same day, except the trip plan. Its run is keyed by the trip's date (`domain/trip-plan-run.ts`), so one missed runs when the service is next up, before the next trip, and only fills open slots. Its notice goes out only on the trip's morning, within four hours of the plan time. Notifications are never retried once one may have gone out.
- The night before (`domain/night-before.ts`, `domain/night-before-reminder.ts`, `night_before` in frontmatter, `nightBefore` on `Recipe`, `RecipeForm` and the model's recipe schemas): one short line of plain words saying what has to happen the evening before. `cleanNightBefore` is the one gate: reading a file, every import (`toDraft`, so link, photo, spoken and Claude's picks), a revision (`checkRevision` refuses the whole answer) and a person's edit (`editRecipe`) all go through it, because the step reaches lock screens and a page may be steering the model. It renders as plain text only. A header's other lines are never rewritten for it by the backfill: `RecipeRepository.addNightBefore` (`recipes/recipe-night-before.ts`) inserts one line, re-reads the file to check nothing else moved, and refuses if the header already has the field, even blank.
- The reminder is the `night-before` job in `jobs.ts`, keyed by the evening's date, through `notifyOnce`. Its time is `household_settings.night_before_time` (Settings → Notifications), falling back to `NIGHT_BEFORE_TIME`, default 17:00; always go through `nightBeforeTime(deps)`. It runs within `REMINDER_WINDOW_MINUTES` (3 hours) of that time and never past midnight. The first look in the window settles the day: with nothing to do it completes without sending, so a swap or plan after that gets no buzz. `NightBeforeNote` and `NightBeforeLine` say what's due instead (`dueForMeal`, `dueForRecipe`), and `TomorrowNote` looks ahead on Today once the time has come. Meals made, skipped or swapped are out; extras are in.
- `nightBeforeCheck` keeps the planner and the dice off such a recipe for today, or for tomorrow from the reminder time on, since nobody would be told. It's deliberately separate from `cookableCheck`: `keepPlanCookable` must never take a planned meal off for this, or the 3 AM top-up would swap out beans someone soaked. A person choosing one isn't stopped, only told.
- The backfill (`application/night-before-backfill.ts`, job `night-before-backfill`, one run ever, key `once`) only runs with a key, and a key added later still gets it. It's the last thing in `runDueJobs`, 15 recipes a request, and its prompt gets the family's rules but no household or pantry, and treats the recipes as material, since they may have come from pages. Failed batches stay for a retry an hour later; recipes already answered are remembered in `household_settings.night_before_reviewed` until it's all done. `scripts/night-before-backfill.ts` runs it on a copy and prints what would change.
- On a phone, meal rows swipe left (toward the check, where the accent mark shows) for done and right for swap (`ui/SwipeRow.tsx`); desktop keeps the buttons, and `.phone-quiet` keeps them for VoiceOver on phones. Swipes starting within the back gesture's `EDGE` are ignored.
- Checking a meal off on Today (`screens/checkin/useMealDone.tsx`, also extras) records `outcome: made` through `markMeal` (a re-check after an uncheck is allowed on a settled meal), then `GET /api/checkin/:date/:slot/questions` (`application/meal-checkin.ts`, `checkinQuestions` for that one meal) opens `MealDoneSheet`: "Any dinner left?" (`AnyLeft`) and the pantry questions (`PantryQuestions`, shared with `PantryStep`). Done sends `POST /checkin/:date/:slot/pantry` (`settleMeal` → `settleMeals` in `checkin-settle.ts`, the same code `recordPantry` uses), which sets `checkinSettled` so the evening check-in doesn't ask again; Not now leaves the questions for it. Unchecking uses `setMealDone(false)` and leaves the pantry as answered. The check-in notification goes out only when `checkinLeftToAsk` (`domain/checkin-open.ts`, `application/checkin-open.ts`) says a meal today is unmarked, a made one still has questions, or a made dinner has no any-left answer; a finished check-in or an empty plan sends nothing.
- One budget per trip, whichever store (`application/budget.ts`). `budgetRoom` gives what's left after the list, and null when more than 2 prices are missing, so nothing spends money it can't see. The room goes to Aldi finds (a slider, Aldi runs only) and then stocking up.
- Stock up (Settings → Stock up, `pantry_items.stock_up`, `domain/stock-up.ts`) is different from Keep stocked: a goal like "10 lb frozen" and a priority. Goals belong to a pantry item: `PUT /api/household/stock-up` takes `pantryItemId`, never a name, and `setStockUpList` won't make an item, so nothing typed can drift from what's on hand. The app adds one by picking from the pantry, and anything new goes in the Pantry first. `fillStockUp` adds a package at a time down the list while the budget allows, and those lines go in the cart. A person's number for the trip wins (`application/trip-plan.ts`). Buying them adds to the goal's portion, from `putAwayStock` when checked off or `storeFromReceipt` from a receipt, without counting twice. A product with no known size gets one package a trip, so setting its usual package on the goal's screen matters.
- Save money (Plan tab, `domain/save-money.ts`, `application/save-money.ts`) compares whole shopping lists with each swap, because a meal's cost depends on what the others already buy. It never offers a swap that adds a line with no price, and nothing changes until someone confirms; swaps go through `setMeal`, so they're pinned. Savings are estimates from known prices.
- A page must never be kept (`http/cache-policy.ts`, `no-store`): going back through history reuses a cached page without rechecking, even under `no-cache`, and an old page loads its old hashed build, which then runs on today's data. `refreshOnReturn` reloads a whole earlier copy restored from memory.
- The Claude chip on the Recipes list (`screens/recipe/ClaudeFilter.tsx`, a native select) includes, hides or shows only Claude's unkept picks (`recipe-filter.ts`). Hiding is a per-phone preference (`hideClaudesPicks`); showing only them isn't kept.
- Walmart's cart link only adds and the app can't read the cart, so `application/walmart-cart.ts` records what the button sent for the trip and the link carries only the rest (`unsentLines`). "Start over" clears the record for when the cart was emptied. The link has already added the items by the time the record is saved, so what's sent is kept on the phone first (`screens/shop/cart-outbox.ts`) and left out of the next link until the server has it; a failure shows with Try again and never stops the link. Don't change the link during its click: the browser follows it after the handlers run.
- The cart quantity on a list line covers the planned meals (`domain/cart-quantity.ts`): the week's needs, less what's counted or in portions, over the product's `packSize`. `minPackages` on the item is only the minimum (1, except produce sold by the each). `packSize` and `minPackages` apply at either store; only `walmartItemId` is Walmart's own. Package sizes come from the product's name on its public Walmart page (`application/walmart-packs.ts`, `domain/pack-size.ts`), read once per product, only with `WALMART_PRODUCT_LOOKUP` on. A recipe's count against a package sold by weight ("2 onions", a 3 lb bag) can't be compared, so it stays at the minimum.
- A line's `packages` (`domain/shopping.ts`) work the same for both stores, and its cost is price × packages. Sizes come from the priced product's name (`packsFromProducts`), then the item's `packSize`; Aldi's own size wins at Aldi. Things sold by weight keep Aldi's estimate ("about 1.85 lb / package") in the product name, and `isEstimate` lines show ≈. Unknown sizes count one and also show ≈.
- The list's sales tax is the grocery rate, not the ZIP's general rate (`domain/grocery-tax.ts`): NC food is a flat 2% statewide. Only NC is filled in; other states show no tax line.
- Dictation never drops audio: each take goes to IndexedDB (`dictation/local-audio.ts`), then `POST /api/recordings` (kept on the server), then `/transcribe`; the session (`dictation/session.ts`) is in localStorage at every step, so failures and reloads land on Retry. A text field's session names its field and stays, audio included, until the words are really in it (`dictation/field-words.ts`): with the field gone, the bar holds them to copy (`words` phase), they go in by themselves when the field offers itself again, even after a reload, and a field that loads its contents passes `ready` only once it has, or the load would write over them. `/api/listen` takes text only. Takes cap at 10 minutes (`RECORDING_LIMIT_SECONDS`) and concatenate.
- Telling Claude what to change in a recipe ("Tell Claude" on the edit sheet) is field dictation, not a `ListenContext`: the answer is a form, not a proposal for the review sheet, and it needs the form as it stands at that moment. `screens/recipe/useRecipeRevision.ts` sends the words and the form to `POST /api/recipes/:slug/revise` (`application/revise-recipe.ts`), which saves nothing; Save is the usual edit. A field that does work with its words returns a promise from `into` (`FieldTaker`, `handOver`), and the session and audio stay until it answers: a failure lands on Retry, and if the sheet closed meanwhile (`'gone'`) the bar holds the words, which go through again on whatever the form holds when this recipe's editor next opens. `domain/recipe-revision.ts` checks every answer and refuses it whole: lines new to the form must read cleanly (`ingredient-line-check.ts`), and lines the person already had aren't held to that. What Claude left alone goes back exactly as sent. The form is locked only while with Claude. Marks and Undo are `revision-history.ts`, and what counts as changed is `domain/recipe-form.ts`. Sheets normally cover the dictation bar; this one raises it above the sheet and over its footer (`useSheetFootHeight`, `dictation.css`). With no key, the mic isn't offered, and words waiting for a recipe stay on the bar. Kitchen notes apply to what Claude writes, and a request against a rule keeps to the rule and says so in the note.
- First-visit tips (`src/client/onboarding`): `OnboardingHost`, mounted once in `App.tsx`'s shell, picks the tip for the route (`tip-route.ts`) and shows it in a `Sheet`; screens know nothing about it. All copy is data in `tips.ts` (title, 2-4 one-line bullets, a `version` to bump when it changes materially); seen state is one localStorage key per phone (`tip-memory.ts`, `cuisine.tips.v1`), marked when shown. It waits for the screen to finish loading (no `.loading` element), shows nothing over an open sheet (`.sheet-backdrop`, so never in the check-in's sheets) and nothing until the household is set up, and only one tip per navigation. Settings has "Show tips again". New screen worth a tip: add it to `tips.ts` and `tip-route.ts`.
- A test copy can serve its own build: `vite build --outDir /tmp/x` and `CUISINE_CLIENT_DIR=/tmp/x`. Don't build into `dist/` for testing; a running install serves it.
- Transcription goes FluidVoice's loopback API first (port 47733), then Parakeet via sherpa-onnx in a child process. Both are optional, as is ffmpeg: with none available, `DictationNotSetUp` gives the person a plain message instead of Retry.
- Every request passes `http/request-trust.ts`: the Host has to be loopback, `PUBLIC_URL`'s host or in `ALLOWED_HOSTS` (`config-rules.ts`), and a write's Origin has to match the Host or `PUBLIC_URL`. A write with no Origin is a script and passes. `tailscale serve` keeps the phone's Host, and the rules also hold if a proxy rewrites it to loopback. Refusals are logged once per host.
- `ACCESS_TOKEN` (`http/access-token.ts`, off by default) gates everything but `/access` and what installing the PWA needs. Browsers use a form and a cookie; scripts use a bearer token. A non-loopback `HOST` won't start without it, unless `ALLOW_OPEN_NETWORK=1`.
- `body()` requires `application/json` and `files()` requires multipart. JSON is capped at 2 MB, uploads at 60 MB and 20 files. A client call with a JSON body must go through `json()` in `api.ts`.
- The CSP (`http/security-headers.ts`) allows no inline scripts or `<style>`/style attributes in HTML, and images only from self, `images.unsplash.com` and `blob:`. React's `style={{}}` is fine. A new outside host or inline script needs a change there; that's why `index.html` loads `public/preferences.js`. The referrer policy stays `same-origin`, since `no-referrer` makes form posts send `Origin: null`. `Markdown.tsx` drops pictures from elsewhere (`domain/image-source.ts`).
- Use cases throw `UserError` (`application/user-error.ts`, with a status) for anything a person should read. Any other error is logged and answered with a generic 500, so plain `Error` messages never reach the screen. Background work stores a `UserError`'s message the same way (a HEIC receipt off macOS) and a generic one otherwise.
- Fetching a link goes through `infrastructure/web/`: `public-address.ts` says what's public, `public-fetch.ts` follows redirects by hand re-checking each, `node-transport.ts` also checks at connect time unless Node is using a proxy (`NODE_USE_ENV_PROXY`), when the proxy resolves names and only the earlier check applies. `html-text.ts` avoids regexes over whole pages on purpose: hostile markup would hang them.
- `recipeFromPage` (`ai/page-import.ts`) gets the family's rules and the pantry with other names like any import, but never the household. It has no tools and its output is a plain-text recipe the family reviews in their own app, and the page is fenced as untrusted text that can't override the rules (`UNTRUSTED_PAGE`). When a site refuses our fetch (401, 403, 429; `site-refused` on the response), the screen asks before `claudePages` (`ai/claude-page-fetcher.ts`) tries Anthropic's web fetch tool: it only fetches, limited to that one site and one use, and the text then takes this same path with no tools. The fetcher is the one call that holds nothing private: keep it that way. Don't make the importer pose as a browser.
- Every recipe import and revision shows the model the pantry with each item's `alsoCalled` (`ai/pantry-list.ts`), and the model reports per ingredient which pantry item it is (`pantryName` on an import's items, `pantryMatches` on a revision). The ingredient text stays as the recipe wrote it. On save (`saveImported`, `editRecipe`), `addOtherNames` (`application/recipe-other-names.ts`, rules in `domain/pantry-other-names.ts`) adds the written name to that item's `alsoCalled` through `updatePantryItem`, for good: unknown pantry names, names the item already goes by (including a name that is only a temporary stand-in), names `findPantryItem` already resolves to it and names of other pantry items are ignored, and only ingredients the saved recipe really has count. A revision saves nothing, so its matches ride back with Save (`RecipeRevision.pantryMatches` out, `RecipeChanges.pantryMatches` in; the edit sheet still has to pass them on).
- Recordings are judged by their bytes (`domain/audio-format.ts`: WebM, Ogg, MP4/M4A), never the client's filename, and ffmpeg gets that demuxer forced with `-protocol_whitelist file`. The store holds 300 recordings or 2 GB, sweeping first; refusing one leaves it on the phone for Retry. The sweep is the daily `recordings-sweep` job. Receipts are capped at 5 GB and are never deleted automatically: they're a household record.
- Push endpoints must be https on a known push service (`domain/push-endpoint.ts`), at subscribe and at send. The VAPID subject is `VAPID_SUBJECT`, or `PUBLIC_URL` if https; otherwise, or with bad keys, push turns off with a log line rather than crashing.
- For your own testing, run a copy on a spare port with `CUISINE_DATA_DIR=/tmp/...` and stop it afterwards.

## Adapting this for your household

A family changes Settings and kitchen notes, not code; see "Adapting it to your family" in the README. When someone does want a code change for their household (another store, another state's grocery tax, a different meal rhythm), keep their personal details out of tracked files: names, ages, addresses and hostnames go in Settings, `.env` or `CLAUDE.local.md`.
